# `.cpfont v4` Font Maker and Catalog Integration Design

## Status and scope

This specification upgrades `crosspoint-cjk-font-maker` so the current CrossPoint format is the primary user flow. The production output is a package of `.cpfont` version 4 files generated by the canonical Python/FreeType converter from `aBER0724/crosspoint-cjk-fonts`.

The existing `legacy-bin` and experimental `xbf2` converters remain available under an explicitly labeled legacy-tools flow. The application also displays the public font catalog generated by `crosspoint-cjk-fonts` GitHub Pages.

Community submission automation and one-click GitHub pull requests remain separate work.

## Goals

- Make `.cpfont v4` the default, recommended format in the UI.
- Generate the seven current physical sizes: `8 / 10 / 12 / 14 / 16 / 18 / 22 pt`.
- Use the same Python/FreeType converter as the public font repository instead of reimplementing its binary format in TypeScript.
- Package the outputs with checksums and build provenance.
- Preserve old `legacy-bin` and `xbf2` behavior for existing users.
- Add a native Font Maker catalog view backed by the Pages `catalog.json` endpoint.
- Keep uploaded private fonts inside the existing local service/storage boundary.

## Non-goals

- The browser does not generate `.cpfont` directly.
- The TypeScript converter does not attempt to emulate FreeType `.cpfont` output.
- The first version does not generate or submit community pull requests.
- The first version does not support multiple font styles in one upload.
- The first version does not host the public catalog's binary assets.
- The first version does not promise identical output when a developer intentionally points at an unpinned local converter checkout; provenance must expose that condition.

## Alternatives considered

### Recommended: Node orchestration around the canonical Python converter

The Node job system remains responsible for uploads, status, storage, and downloads. A dedicated runner invokes `crosspoint-cjk-fonts/scripts/fontconvert_sdcard.py` from a compatible toolkit checkout. Production Docker pins an exact toolkit commit. This keeps a single binary-format implementation and makes local and production behavior auditable.

### Rejected: rewrite `.cpfont v4` in TypeScript

A browser or Node rewrite would duplicate Unicode intervals, FreeType rasterization, 2-bit quantization, metrics, kerning, ligatures, fallback behavior, and binary packing. Passing a few header tests would not establish byte-level compatibility.

### Deferred: submission-package-only workflow

Generating metadata locally and asking GitHub Actions to build fonts remains appropriate for community contributions, but it does not satisfy ordinary users who want to convert and download a private font without a GitHub account.

## Application information architecture

The main navigation becomes:

```text
Font Library | Make .cpfont | Legacy Tools
```

- **Font Library** displays the public Pages catalog and direct Release downloads.
- **Make `.cpfont`** is the default conversion route.
- **Legacy Tools** contains the current `legacy-bin` and experimental `xbf2` controls.

The current one-page converter is split into focused React components while preserving shared theme, locale, PWA, preview, and history behavior.

## Canonical converter integration

### Local development

The runner resolves the toolkit root in this order:

1. explicit `CPFONT_TOOL_ROOT` environment variable;
2. the sibling checkout `../crosspoint-cjk-fonts` relative to the Font Maker repository;
3. otherwise unavailable, with an actionable capability error.

A compatible toolkit must contain:

- `scripts/fontconvert_sdcard.py`;
- `scripts/cpfont_version.py` declaring version `4`;
- `scripts/fetch_fallback.py`;
- `requirements.txt`;
- `vendor/NotoSans-Regular.ttf` after setup.

Local setup uses a documented command to install the toolkit requirements and fetch the SHA-256-locked fallback before starting conversions.

### Production Docker

The production image uses Debian rather than Alpine so Node, Python, and FreeType runtime behavior is predictable. During the image build it:

1. installs Python 3, a virtual environment, Git, and CA certificates;
2. clones `aBER0724/crosspoint-cjk-fonts`;
3. checks out an exact `CPFONT_TOOL_COMMIT` build argument;
4. installs the pinned Python requirements into a virtual environment;
5. runs `scripts/fetch_fallback.py` once;
6. sets `CPFONT_TOOL_ROOT` and `CPFONT_PYTHON` for the runtime.

The image build fails if the checked-out toolkit does not declare `.cpfont` version 4.

The initial pin is the currently verified toolkit commit:

```text
c242803dbd47f13fa5886bf0701db72871709d23
```

Updating this pin is an explicit maintenance change with converter compatibility tests.

## `.cpfont v4` job contract

`output_format` accepts a new literal:

```text
cpfont-v4
```

The web application sends it explicitly. An omitted API value retains the historical `legacy-bin` behavior for compatibility with existing callers.

A `.cpfont` job adds:

- `family_name`: normalized output family name;
- `force_autohint`: optional boolean, default `false`.

Legacy-only fields such as `tier`, `font_size_px`, `output_width_px`, `output_height_px`, `font_weight`, and `compat_flip_y` are ignored by the `.cpfont` runner and remain valid only for legacy formats.

The API validates the selected format before scheduling and rejects unsafe family names. The normalized family identifier uses ASCII letters, digits, `_`, and `-`, is at most 64 characters, and cannot contain a path separator or dot segment.

## Conversion execution

A dedicated Node `CpfontRunner` interface isolates process execution:

```ts
interface CpfontRunner {
  convert(input: CpfontConversionInput, onProgress?: (progress: ConvertProgress) => void): Promise<CpfontPackage>;
}
```

The production implementation:

1. creates a job-specific temporary directory;
2. writes the uploaded TTF/OTF with a safe filename;
3. invokes Python without a shell;
4. passes `--style regular`;
5. passes the locked Latin fallback as `--fallback-regular`;
6. passes `--intervals latin-ext,cjk`;
7. passes `--sizes 8,10,12,14,16,18,22`;
8. passes the normalized family name and isolated output directory;
9. enforces a configurable timeout, default 15 minutes;
10. kills the child process on timeout or server shutdown;
11. validates every generated file before packaging;
12. deletes the temporary directory in a `finally` block.

The process never uses `shell: true` and never interpolates user values into a command string.

Because the canonical converter does not expose per-glyph machine progress, `.cpfont` jobs report coarse phases:

- `preparing` — 5%;
- `rasterizing` — 10% until the process exits;
- `validating` — 85%;
- `packaging` — 92%;
- `done` — 100%.

Converter stderr is capped and included in a safe failed-job message without leaking server paths.

## Output validation and package

Before accepting output, Font Maker validates:

- exactly seven expected filenames exist;
- every file has magic `CPFONT\0\0`;
- every file declares version `4`;
- each file has one regular style;
- TOC and section boundaries remain inside the file;
- no unexpected file or symbolic link is included;
- each file stays below the configured output limit;
- total package size stays below the configured package limit.

The downloadable ZIP is deterministic and named:

```text
<Family>_cpfont-v4.zip
```

Its contents are:

```text
<Family>/
├── <Family>_8.cpfont
├── <Family>_10.cpfont
├── <Family>_12.cpfont
├── <Family>_14.cpfont
├── <Family>_16.cpfont
├── <Family>_18.cpfont
├── <Family>_22.cpfont
├── SHA256SUMS
└── build.json
```

`build.json` contains:

- package schema version;
- `.cpfont` version `4`;
- physical size groups;
- interval policy `latin-ext,cjk`;
- source filename and SHA-256;
- fallback SHA-256;
- converter repository URL and Git commit;
- Python and relevant dependency versions;
- `force_autohint` value;
- output filenames, byte sizes, and SHA-256 values.

ZIP entry order, permissions, and timestamps are fixed. The package contains no source TTF/OTF by default.

## Job storage and existing Windows race

Before adding long-running `.cpfont` jobs, the file-system job state writer must stop generating temporary filenames from only `process.pid` and `Date.now()`. Concurrent progress writes currently collide on Windows and produce `EPERM` during rename.

The storage implementation will use a cryptographically random or monotonic unique suffix and serialize writes for each job path. A regression test performs concurrent writes and verifies that the final JSON remains valid and no temporary file is shared.

This baseline fix is required because `.cpfont` coarse progress and status polling still create overlapping state updates.

## Upload and resource limits

The existing upload ceiling remains `20 MiB`, and the UI validates it before upload. Supported inputs remain `.ttf` and `.otf`.

Additional limits are explicit configuration:

- conversion timeout: 15 minutes;
- generated single file: 50 MiB;
- generated package contents: 350 MiB;
- retained stderr: 64 KiB.

A limit failure produces a stable API error code and a user-facing phase-specific message. Rate limiting remains unchanged.

## Browser UI for `.cpfont`

The current format page shows:

- font file selector;
- detected font family name, editable before conversion;
- the fixed physical sizes, separated as UI `8/10/12` and reader `14/16/18/22`;
- the fixed Unicode policy `Latin Extended + CJK`;
- optional “force auto-hinting” advanced control;
- a statement that the package uses actual physical files and is not scaled on device;
- source file size and the 20 MiB limit before submission;
- phase-aware conversion status;
- ZIP download and conversion history.

Font metadata extraction uses the already loaded `opentype.js` parser for names only. It does not participate in `.cpfont` rasterization.

The existing device canvas remains an approximate source-font preview and is labeled accordingly. It must not be described as the final `.cpfont` bitmap. Links to the public catalog show examples rendered from actual `.cpfont` data.

## Legacy tools

The existing controls remain unchanged in behavior:

- character tiers `6k / 24k / 65k`;
- font size and synthetic weight;
- output width and height;
- Y-axis compatibility mode;
- `legacy-bin` and experimental `xbf2`.

The UI and documentation explicitly state that these formats are not the current SD-card `.cpfont v4` catalog format. Existing API requests and output filenames continue to work.

## Public font catalog integration

Font Maker reads:

```text
https://aber0724.github.io/crosspoint-cjk-fonts/catalog.json
```

The URL is configurable at build time with `VITE_FONT_CATALOG_URL`. A separate `VITE_FONT_CATALOG_PAGE_URL` controls the “Open full catalog” link.

A focused catalog client validates:

- web schema version `1`;
- `.cpfont` version `4`;
- manifest version `2`;
- family and file array shapes;
- HTTPS download and preview URLs.

The Font Library route provides search, license/status labels, preview-size selection, and direct downloads. It does not proxy Release assets through the Font Maker server.

If loading fails, the route displays a concise retry state and preserves an external link to the full catalog. Conversion features remain available.

## API capability endpoint

`GET /api/capabilities` reports public, non-secret runtime facts:

```json
{
  "cpfont": {
    "available": true,
    "version": 4,
    "sizes": [8, 10, 12, 14, 16, 18, 22]
  },
  "legacyFormats": ["legacy-bin", "xbf2"]
}
```

When unavailable, it returns `available: false` and a stable reason code such as `ERR_CPFONT_TOOL_MISSING` without exposing local filesystem paths.

The UI disables submission, not the whole page, and links to setup documentation.

## Failure behavior

Stable errors distinguish:

- invalid input extension or size;
- invalid family name;
- missing or incompatible toolkit;
- missing locked fallback;
- Python process start failure;
- conversion timeout;
- converter failure;
- invalid `.cpfont` output;
- package size limit;
- output storage failure.

Failed jobs preserve the last phase and a safe error message. Temporary uploads and generated files are cleaned according to the existing storage lifecycle.

## Testing

All behavior changes follow test-first development.

Vitest coverage includes:

- unique atomic state writes under concurrency;
- `cpfont-v4` API acceptance and unsafe-name rejection;
- omitted format retaining legacy compatibility;
- toolkit capability detection;
- child-process arguments passed as an array without a shell;
- timeout and cleanup behavior;
- output header and seven-size validation;
- deterministic package filename, entry order, hashes, and provenance;
- legacy conversion regression tests;
- catalog schema parsing and failure fallback;
- `runWebFlow` submitting `cpfont-v4` and reporting coarse phases;
- UI copy in Chinese, Japanese, and English clearly separating current and legacy formats.

A real converter integration test is opt-in locally and mandatory in Docker/CI. It builds a tiny synthetic-font fixture over a small test interval through the canonical converter, verifies version 4, and avoids generating a full CJK package during every unit test.

The production build gate remains:

```bash
npm test
npm run build
```

Docker verification additionally builds the image and calls `/api/capabilities`.

## Acceptance criteria

- Font Maker opens on the `.cpfont v4` workflow.
- A supported TTF/OTF produces a ZIP containing exactly seven valid version 4 files, checksums, and provenance.
- The converter used is the canonical `crosspoint-cjk-fonts` Python/FreeType implementation at a recorded commit.
- `legacy-bin` and `xbf2` remain usable and clearly labeled as legacy/experimental.
- The Font Library route displays the Pages catalog and direct Release downloads.
- A catalog outage does not block private conversion.
- Uploaded font data is not sent to the public catalog or GitHub.
- Windows file-system integration tests no longer fail from temporary job-state filename collisions.
- `npm test`, `npm run build`, and the production Docker capability check pass.
